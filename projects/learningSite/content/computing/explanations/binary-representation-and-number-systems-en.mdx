Every value inside a computer, at the hardware level, is stored as a sequence of bits -- individual physical switches that are reliably either off or on. This is not an arbitrary design choice: building a component that reliably holds and distinguishes exactly two electrical states is far simpler and more robust than building one that must reliably distinguish ten different voltage levels the way a decimal digit would require. Binary (base 2) is a direct engineering consequence of that hardware reality, not a stylistic preference. Hexadecimal (base 16) shows up constantly in programming purely as a human convenience layered on top of that same binary reality -- since 16 is a power of 2, each single hex digit corresponds to exactly four bits, so a long, hard-to-read binary string can be written far more compactly in hex without changing anything about what's actually stored.

Representing negative integers takes a specific scheme called two's complement, and the reason it's used instead of a simpler sign-bit approach (a plus/minus flag stuck in front of an otherwise-unsigned number) comes down to hardware efficiency: two's complement is constructed so that the exact same binary addition circuit that already correctly adds two positive numbers also correctly adds a positive and a negative number, or two negative numbers, with no separate subtraction circuit required at all. To find a number's negative in two's complement, you flip every bit and add one -- and adding that result to the original number using ordinary binary addition genuinely produces zero (with the extra overflow bit simply discarded), which is precisely the property that makes one addition circuit sufficient for all four combinations of signs.

Floating-point representation extends this finite-bits idea to real numbers by storing a sign bit, an exponent, and a fraction (mantissa), rather than attempting to store arbitrarily many decimal digits. This is exactly why a value like 0.1 cannot be stored exactly: 0.1 has no finite representation in binary, for the same underlying reason 1/3 has no finite representation in decimal -- some fractions simply don't terminate in some particular base. The floating-point format stores the closest value it can actually represent, and that tiny, well-understood, entirely predictable rounding error is why 0.1 + 0.2 doesn't print as exactly 0.3 in virtually every mainstream programming language, not a flaw specific to any one of them.
