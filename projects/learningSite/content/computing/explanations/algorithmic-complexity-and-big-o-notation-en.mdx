Big-O notation exists to answer one specific question: as the input to an algorithm grows, how does the amount of work grow with it? It deliberately ignores the actual machine, the actual programming language, and the actual constant multipliers involved in an implementation, because those details vary from system to system while the underlying growth-rate relationship does not. An algorithm is O(n) if the work required scales linearly with input size n -- process twice as much data, do roughly twice as much work. An algorithm is O(n^2) if the work scales with the square of the input -- twice as much data means roughly four times as much work, a much steeper penalty for growth.

This growth-rate focus is exactly why Big-O drops constant factors and lower-order terms. An algorithm that does 5n + 100 operations is still O(n), because as n grows large, the 5 and the 100 become irrelevant compared to the n term itself -- they don't change how the algorithm scales, only its absolute cost at any fixed size. This is also exactly why a real-world benchmark can show a "worse" algorithm winning at small input sizes: an O(n^2) algorithm with a very small constant factor can beat an O(n log n) algorithm with a large constant factor, right up until the input grows past whatever crossover point makes the growth-rate difference dominate.

The standard complexity classes form a rough hierarchy that's worth internalizing: O(1) constant-time operations (like accessing an array by index) don't get slower as data grows at all; O(log n) operations (like binary search) get only slightly slower as data grows, since each step roughly halves the remaining work; O(n) operations scan the data once; O(n log n) operations, common in efficient sorting algorithms, combine a linear pass with a logarithmic factor; O(n^2) operations, common in naive nested-loop algorithms, get dramatically slower as data grows; and O(2^n) exponential-time algorithms become impractical past even modest input sizes. Recognizing which class a piece of code belongs to -- usually by counting how deeply loops are nested over the input -- is what lets an engineer predict whether code that works fine in testing will still function at all once real-world data volumes arrive.
