Every working recursive function is built from exactly two cooperating parts. The base case is the simplest possible version of the problem, one the function can answer directly without calling itself again -- for factorial, that's 0! = 1. The recursive case handles everything else by reducing the problem to a smaller version of itself and combining that smaller result to produce the current answer -- for factorial, n! = n * (n-1)!, where (n-1)! is computed by the function calling itself with a smaller input. Every recursive algorithm, no matter how elaborate, reduces to this same two-part pattern.

The call stack is what makes this actually work at the machine level. When a function calls itself, the current call doesn't vanish -- it pauses, waiting for the call it just made to finish, and that pending, paused state gets pushed onto a stack of similarly pending calls. This is why the actual order of computation unwinds backward: the innermost call (the one that finally hits the base case) computes its answer first, then returns that answer to the call that invoked it, which combines it into its own answer and returns in turn, and so on back out to the original call. It's also exactly why a recursive function with no reachable base case is dangerous in a specific way: rather than looping forever the way a broken while-loop might, it keeps adding new entries to the call stack with every self-call, and since none of those calls can return until a base case is hit, the stack keeps growing until the program runs out of memory allocated for it and crashes with a stack overflow -- a distinctly different failure mode from an infinite loop, which can run forever without ever running out of memory.

Recursion and iteration are not different computational powers -- they're different ways of expressing the same underlying computation. Any recursive algorithm can be mechanically rewritten as a loop that manages its own explicit stack data structure to track the same pending work the call stack would otherwise track automatically, and many compilers even perform this transformation automatically for a specific, common pattern called tail recursion. What makes recursion genuinely useful, rather than just an alternative notation, is that some problems are themselves most naturally defined in terms of smaller versions of themselves -- traversing a tree's branches, or computing a value defined by a recurrence relation -- and for those problems, a recursive solution can be far easier to read and reason about correctly than the equivalent iterative one with its own explicit stack management.
