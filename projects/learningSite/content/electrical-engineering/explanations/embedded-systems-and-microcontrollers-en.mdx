A general-purpose CPU is designed around one overriding goal: run arbitrary software as fast as possible, with memory, caching, and instruction execution all optimized for raw throughput on workloads the chip designer can't predict in advance. A microcontroller starts from a completely different brief: run one known, fixed program that has to sense and respond to the physical world, as cheaply and reliably as possible. That difference in goal is why a microcontroller integrates the processor core with memory and the specific peripherals (timers, ADCs, UART/SPI/I2C communication interfaces, general-purpose I/O pins) a physical device actually needs directly onto one chip, rather than assuming those functions will be provided by separate components the way a desktop system does.

Interrupts are the clearest expression of what that integration buys. A polling loop -- code that repeatedly checks whether a button has been pressed or a sensor threshold crossed -- ties up the processor's attention the entire time it's checking, and worse, the delay between an event happening and the loop getting around to checking for it is unpredictable if the processor has other work queued up. An interrupt instead lets a hardware event directly force the processor to stop whatever it's doing and jump to a dedicated handler routine, immediately and regardless of what else was running. That's what makes a genuinely bounded, predictable response time possible -- exactly the kind of hard real-time guarantee an embedded system controlling physical machinery or safety equipment actually needs, and that ordinary desktop software, with no hard deadline to meet, doesn't have to provide.

None of this comes free, though. Every additional peripheral, every extra kilobyte of memory, and every increase in clock speed costs real silicon area, draws more current, and dissipates more heat. For a device running off a coin-cell battery for years, or manufactured by the million at the lowest possible cost, those costs are the actual design constraint -- which is why embedded design is fundamentally a series of tradeoffs against power, cost, and real-time responsiveness, not simply a smaller-scale version of desktop computer design.
